# landlord-mapper-web

Railway deployment of the Austin landlord-mapper web tool. Personal dev
environment.

The app answers four questions an organizer actually walks in with: who owns my
building, what else does that landlord own, who are the biggest landlords here,
and give me the list as a CSV. Data is Texas county appraisal rolls joined to
Texas Comptroller franchise-tax filings.

## What is here

| File | Role |
| --- | --- |
| `server.py` | The whole application. Stdlib only, no framework, no pip install. Reads a SQLite database read-only. |
| `build-db.py` | Builds that database from the pipeline's CSV output. Writes `.building` then renames, so a rebuild is atomic. |
| `Dockerfile` | Python 3.12 slim + tini. Does *not* contain the database. |
| `entrypoint.sh` | Bridges Railway's `$PORT` to the `$LM_PORT` the app reads, seeds the volume if empty, then waits rather than exits if it is not seeded. |
| `typed.py` / `retype.py` | The typing pass that took the database from 1.80 GB to 1.14 GB, and a standalone retype-in-place driver. `build-db.py` imports `typed`. |
| `seed-chunked.sh` | Fallback seeder for a host without object storage: splits the archive across deploys and stages parts on the volume. |
| `seed-image.sh` | Earlier single-deploy seeder. Kept only for a database small enough to fit the upload cap, which this one is not. |
| `railway.toml` | Dockerfile builder, one replica, restart on failure. Deliberately no healthcheck yet — see the file. |

## The one thing that is not in git

**The database.** It is 1.14 GB (1,138,601,984 bytes) and the source CSVs are
another 700 MB.
Both are regenerated by `build-db.py` from the R pipeline's output, so neither
belongs in a repo, and neither belongs in the image either — they change on a
data refresh, not a code change, and baking them in would re-upload a gigabyte
on every code deploy.

The database lives on a Railway volume mounted at `/data`, and the app reads it
via `LM_DB=/data/lm.sqlite3`.

## Deploying

```
railway up --service web
```

## Seeding the volume

First deploy comes up with an empty volume. `entrypoint.sh` logs that it is
waiting and blocks; it does not exit. That is deliberate — an entrypoint that
died on first boot could never be seeded at all, and waiting also means seeding
completes itself with no restart.

### Three routes were tried. Only one works

| Route | Outcome |
| --- | --- |
| Pipe over `railway ssh` | **8 MB of stdin never finished in 5 minutes.** Also intermittently swallows the first line of stdout. Not a data channel. |
| Whole archive in the image | **413 Payload Too Large** at 499 MB |
| 350 MB chunks in the image | **413 again** at 361 MB, so the cap is far below that |
| **Object storage + presigned URL** | **Works.** One upload, no size limit in play |

### What works: the container fetches it itself

The gzipped database lives in a Railway bucket. `LM_SEED_URL` holds a presigned
GET, so no credentials live in the container, and the deploy-size cap stops
mattering entirely.

```
# 1. compress on the machine that BUILT it (128 cores beats one)
pigz -6 -p 16 -c lm.sqlite3 > lm.sqlite3.gz

# 2. upload to the bucket (S3-compatible; creds from `railway bucket credentials`)
aws s3 cp lm.sqlite3.gz s3://$BUCKET/lm.sqlite3.gz --endpoint-url $ENDPOINT

# 3. presign, and point the service at it
aws s3 presign s3://$BUCKET/lm.sqlite3.gz --expires-in 43200 --endpoint-url $ENDPOINT
railway variables --set "LM_SEED_URL=<presigned>" --set "LM_DATA_VERSION=<new-version>"
railway up --service web --ci
```

The fetch uses stdlib `urllib` and decompresses streaming, because `curl` is not
in `python:3.12-slim` and buffering a gigabyte in memory is not an option.

`seed-chunked.sh` remains as a fallback for a host without object storage. It
proves the parts reassemble to the same sha256 *before* spending any upload time.

### `LM_DATA_VERSION` is what makes a refresh possible

Every seed path is guarded by "if the database is absent". That is correct for a
restart and **wrong for a data refresh**: the volume persists, so new data would
never be picked up and the service would keep serving stale numbers with no error
anywhere to notice.

So the volume is stamped with the version it was seeded at. Change
`LM_DATA_VERSION` and the next boot retires the old database, seeds the new one,
and discards the old file only on success. **If the seed fails it restores the
previous database, keeps serving, and deliberately does not advance the stamp** —
stamping there would make the next boot believe the refresh already happened.

Leave `LM_DATA_VERSION` unset for the original never-replace behaviour.

## After the first successful serve

Add the healthcheck back to `railway.toml`:

```toml
healthcheckPath = "/health"
healthcheckTimeout = 30
```

It is safe from then on: the volume is persistent, so restarts find the database
already there, and the check only reports real failures.

## Performance notes worth keeping

These were measured under a 1 GB memory cap on droplet-shaped disk, with cold
cache asserted per request via `posix_fadvise` + `mincore`. They apply to any
memory-capped container, Railway included.

- **RSS is 152–165 MB steady, 183 MB worst observed.** Startup is instant; it
  opens the database rather than loading it. An earlier in-memory design used
  3.09 GiB and took 48 s to start.
- **`parcel` was 796.5 MB and is now 378.6 MB**; `ix_p_addr` is 82.9 MB. The
  `search()` query still carries an explicit `INDEXED BY ix_p_addr`, which was
  load-bearing at the old size: on a memory-capped host the 796.5 MB table never
  fit page cache, so every address search cost ~2.8 s *and* evicted everything
  else — `/rankings` measured falling from 0.179 s to 4.469 s on the request right
  after one search. At 378.6 MB the table plausibly fits now, so the hint may no
  longer be needed. It has not been re-measured post-typing, so it stays.
- **The full 250k-row CSV export is the only route that can exceed 15 s.** Watch
  proxy read timeouts if you front it with anything.
- **Sleep-on-idle is viable** now that startup is instant. For bursty traffic
  that is the largest single saving available on a metered host.
